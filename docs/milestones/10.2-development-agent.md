# 10.2 — Development Agent

[Indice](README.md) · [Progetto](../../README.md)

**Stato: IMPLEMENTATA V1, provider di prototipi statici.** Genera un visual scaffold e una checklist da task di un piano approvato. Comportamento applicativo, storage e criteri di accettazione del prodotto restano da implementare e verificare. Il piano della 10.1 mantiene `execution_authorized=false`.

## Obiettivo e scelte

Passare dal piano revisionato ad artefatti riproducibili e ispezionabili, senza esecuzione, installazioni, rete, spese o distribuzione. La richiesta esplicita di generazione e un'azione distinta dalla sola approvazione del piano; l'export su disco richiede una richiesta separata.

La v1 usa `static-prototype-v1`, un template deterministico senza modello remoto. Un LLM non configurato introdurrebbe costi, credenziali e risultati non riproducibili: non viene simulato. Il protocollo Python `DevelopmentProvider` permette future implementazioni esplicite; l'API accetta solo il provider statico, non plugin indicati dal chiamante.

Bundle di file completi anziche patch su un checkout: nessuna sovrascrittura di sorgenti esistenti, working tree o dipendenze. Il provider non contiene comandi shell, npm/pip o installazioni.

## Componenti e integrazione

- [Agente e provider](../../backend/app/agents/development.py): `DevelopmentAgent`, contratto `Agent.execute(Task) -> str`, generazione pura e registrazione esplicita.
- [Modelli](../../backend/app/development/models.py): file UTF-8, manifest SHA-256, percorsi portabili e limiti.
- [Servizio](../../backend/app/development/service.py): piano letto dal database, approvazione, versioni, audit e idempotenza.
- [Workspace](../../backend/app/development/workspace.py): staging privato, rename locale e verifica dei contenuti esistenti.
- [API](../../backend/app/development/router.py): endpoint aggiuntivi; contratti precedenti compatibili.

Serve un piano persistito `ready_for_review`, con revisione `approved` e versioni correnti di tutte le venture del confronto sorgente. Report o flag di approvazione nel payload API non sono accettati. I task selezionati devono esistere e includere tutte le proprie dipendenze. L'ordine deriva dal piano.

L'agente puro riceve un `DevelopmentContext` risolto dal coordinatore. Non accede a database o filesystem e non autentica JSON di terzi. Registrarlo in `AgentRegistry` non autorizza ulteriori azioni.

## Contratti e API

`POST /development-artifacts`, header `Idempotency-Key` obbligatorio:

```json
{
  "plan_id": "00000000-0000-0000-0000-000000000001",
  "task_ids": ["t1"],
  "actor": "developer",
  "reason": "Preparare un prototipo visuale per revisione",
  "target": "static-prototype-v1"
}
```

Sostituire ID piano e task con quelli reali. Ammessi 1-100 task unici. Risposta 201 con `report` e `export` inizialmente null. Report: richiesta, ID/data UTC, piano completo con evidenze e approvazione, bundle, ordine task e `bundle_sha256`.

File generati:

- `index.html`: obiettivo, deliverable e checklist statici; testo escapato, nessuno script, form o servizio remoto, CSP restrittiva.
- `scope.json`: requisiti pertinenti, task, stime dichiarate, rischi, ipotesi, esclusioni e limitazioni.
- `REVIEW.md`: istruzioni locali e controlli umani pendenti.

`completion=prototype_requires_review` non dichiara task completati o criteri superati. File e manifest sono deterministici per lo stesso piano e selezione; ID e timestamp della ricevuta possono differire. Non vengono inventati risultati di test o esperimenti.

`GET /development-artifacts/{id}` restituisce lo storico persistito e verifica la catena di impronte del bundle, senza nuove azioni.

`POST /development-artifacts/{id}/export`:

```json
{"actor": "reviewer", "reason": "Ispezionare il prototipo nel workspace locale"}
```

Export disabilitato di default (503). Configurare una root dedicata prima dell'avvio, per esempio in PowerShell:

```powershell
$env:DEVELOPMENT_WORKSPACE_ROOT = "C:\Users\Utente\Documents\JACK-workspaces"
```

Nessun path nel payload API. Il server usa solo `<root>/<artifact UUID>` e aggiunge `manifest.json`: versione schema/provider, ordine task, stato e percorso, dimensione UTF-8 e SHA-256 di ogni file. `bundle_sha256` e il digest del manifest JSON canonico (chiavi ordinate, separatori compatti, stringhe ASCII); il file manifest aggiunge un LF finale.

La prima esportazione registra autore/motivo, data, path e digest. Stessa richiesta: controlla nuovamente versioni e contenuti e restituisce la ricevuta originale. Autore/motivo diversi o root cambiata: 409. File modificati, mancanti in una directory esistente o aggiunti dall'esterno: 409 senza sovrascrittura. Una directory completamente rimossa puo essere ricreata con una richiesta identica valida; la ricevuta rimane storica.

Errori: 404 risorsa mancante; 409 piano non approvato, versioni obsolete, chiave riutilizzata con payload diverso o conflitto; 422 input/target/task non valido; 503 export disabilitato o filesystem indisponibile. Ripetere una generazione registrata restituisce lo storico anche se il portafoglio e cambiato: non autorizza un nuovo export.

## Persistenza, concorrenza e recupero

[Migrazione 102_development](../../backend/alembic/versions/102_development.py), dopo `101_planning`: tabella `development_artifacts` con chiave unica, richiesta/report JSON immutabili e una ricevuta export scritta tramite compare-and-set. Nessuna modifica a budget, spese, task o tabelle precedenti.

La generazione salva prima il bundle senza scrivere file. L'export prepara e verifica una directory temporanea privata sotto la root, poi la sposta al nome finale. Un errore nello staging ripulisce solo quella directory. Un errore nel commit SQL non cancella i file finali: il retry li verifica e registra la ricevuta mancante.

Filesystem e database non sono una transazione distribuita. Un crash puo lasciare staging o file senza ricevuta: non rimuoverli alla cieca, ispezionare o ripetere la richiesta identica. Il downgrade elimina la nuova tabella e gli audit, non gli export gia presenti. I test verificano la catena completa, operazioni reali, downgrade preservando un piano approvato 10.1 e nuovo upgrade, su database temporaneo. Nessuna migrazione di verifica sul database locale.

## Sicurezza, limiti e verifiche

Percorsi relativi ASCII portabili; vietati traversal, assoluti, backslash, alternate data stream, nomi Windows riservati, dotfile e collisioni senza distinzione maiuscole/minuscole. Limiti: 100 file, 262144 byte per file e 1048576 byte totali. `manifest.json` riservato. Rifiutati symlink e reparse point/junction, anche negli antenati della root. Il workspace esistente deve corrispondere esattamente al bundle.

Questo e contenimento dei percorsi in una root dell'operatore, non un isolamento OS contro processi con accesso in scrittura. Processi ostili possono introdurre race nel filesystem. Il runtime e la separazione di privilegi restano nella 10.3. `actor` resta dichiarato, senza autenticazione/RBAC: usare un confine fidato. Audit immutabile tramite servizio, non contro SQL diretto. La verifica versioni fotografa il controllo e non blocca futuri cambiamenti.

[Test dedicati](../../backend/tests/test_development.py): approvazione, dipendenze, determinismo, escaping, snapshot, idempotenza, freschezza, manifest, traversal, symlink/junction, conflitti, errori parziali, concorrenza, recupero e migrazioni. Eseguire anche suite completa, Ruff check/format, Pyright e `git diff --check`.
